# アプリ統合向け全文差分アルゴリズム検証（2026-07-29）

## 結論

`full-rewrite-safe` が返した修正版全文を、アプリ側で独立した局所置換へ安全に変換できる。
保存済みの実応答175件を再解析し、175件すべてを受理した。誤り5例×10回から期待どおり
60件（1誤りの4例×10件、2誤りの1例×20件）を抽出し、文体保護25例×5回は0件だった。

この検証では Gemini API を呼んでいない。既存JSONとローカルの自己テストだけを使用したため、
追加料金は発生していない。

## アルゴリズム

1. CRLF / LF を同じ改行として扱い、Unicode の書記素単位へ分割する。
2. Myers 差分で修正前後の最短編集列を求める。
3. 1語内で最大2書記素を挟む差分を1提案へまとめる。
4. 純粋な挿入は隣接1書記素を借り、範囲を持つ置換へ変換する。
5. 書記素位置を UTF-16 オフセットへ戻し、前後最大20書記素の文脈を付ける。
6. 全提案を原文へ逆順適用し、修正版全文を再現できることを必須条件にする。
7. 過剰な変更、重複範囲、大きすぎる変更箇所、編集距離超過は応答全体を破棄する。

## オフラインテスト

- 固定境界テスト: 13/13 PASS
  - 置換、複数変更、挿入、先頭挿入、削除
  - サロゲートペア、結合文字
  - CRLF / LF、末尾改行、Markdown
  - 空文書への挿入拒否、大規模書き換え拒否
- 固定シードによるランダム編集の往復テスト: 200/200 PASS
- TextAnchor の追従・範囲編集時の失効・順次適用: PASS
- 保存済み `full-rewrite-safe` 応答: 175/175 受理
- 抽出提案: 60件
- 文体例からの提案: 0件
- 応答全体の破棄: 0件

実行コマンド:

```powershell
dotnet run --project PromptValidation -- --self-test
dotnet run --project PromptValidation -- --analyze-results PromptValidation/results
```

## 本体統合

- `DocumentDiff` を `Proofreading/` へ移し、本体と検証アプリが同じソースを使うようにした。
- 各タブは校正結果を初めて受け取るときに `ProofreadingSession` を遅延生成する。
- セッションは開始・終了の `TextAnchor` を保持し、提案外の編集へ追従する。
- 提案範囲と交差する編集ではその提案だけを失効させる。
- 許可時はアンカー範囲が `Original` と一致する場合だけ置換する。

## 表示方針

全文方式ではモデルから提案ごとの理由・カテゴリを受け取らない。固定値を表示する意味もないため、
提案モデルには保持せず、UIにも表示せず、リアクション履歴にも保存しない。
分類・理由生成だけの追加 API 呼び出しは行わない。ユーザーが入力する拒否理由は別に保持する。
